# Wingfoil 9.1.0

A behaviour release: a historical `RunFor::Forever` run now ends when its data
does.

## A `channel` at end-of-stream ends a `Forever` historical run

A `RunMode::HistoricalFrom` run bounded by `RunFor::Forever` used to stop only
when its scheduler had nothing left to run. A graph with a `channel` feed and
any other source that schedules — a `ticker` is the usual one — therefore kept
cycling after the feed closed, engine time walking forward until `NanoTime`
overflowed ([#978](https://github.com/wingfoil-io/wingfoil/issues/978)).

The run now ends once every `channel` receiver has drained **and** the work
those feeds can still drive has run. A `delay`, a `feedback` or anything else
scheduled downstream of a feed still fires before the stop; a `ticker` is a
heartbeat rather than a feed, so it no longer holds the run open. Several
channels are counted per receiver, so a graph merging feeds of different lengths
replays the longest instead of stopping at the first close.

`RunFor::Duration` and `RunFor::Cycles` are unchanged: the explicit bound owns
the stop, so a bounded backtest keeps ticking after its data ends — the tail for
settlement, funding or a final mark. Realtime still ends on the first channel
close, matching its waker-driven model.

## What to do

An existing bounded run needs no change. A `channel` + `ticker` graph under
`RunFor::Forever` that relied on outliving its data was already broken by the
overflow; it now stops where the data does. A graph that genuinely needs a tail
after the feed closes should bound the run — `RunFor::Duration` is the number
that says how much tail.
