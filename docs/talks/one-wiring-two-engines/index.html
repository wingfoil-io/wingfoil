The problem

Everything ticks at a different rate

You control the rates too

sample · throttle · window · buffer · distinct · merge · split

Nanoseconds per node

Not microseconds.

90 seconds. Set up the whole talk here: three feeds, three rates, none of them aligned, and the rate itself is something you need to control rather than something handed to you. Be precise about the grouping, because someone will push back on the word "burst": the point is that many messages carry the SAME exchange timestamp — one aggressive order sweeping several levels is several fills at one instant. That is a property of the data, not of how fast you are reading it. Wingfoil delivers same-timestamp values together and never collapses them to latest-wins, because a strictly-monotonic clock means a split same-time group cannot be reassembled afterwards. Then: performance. Nanoseconds per node. That constraint is what rules out most of the obvious answers, which is the next slide.

The solution

You need a DAG

  • Wire a graph of calculations — declared once.
  • Topologically sorted — every node runs after everything it reads, once per tick.
  • Only what's active — not the whole graph.
  • The framework decides what to compute, and when.

This is the thesis of act one — state it flat, then spend the next two slides earning it. Don't over-explain "doubles every level" here; slide 6 is the demonstration and slide 7 is the chart. The fourth bullet is the one to lean on: the framework's job is deciding what to compute and when. Everything after this slide is how that is actually done. Backup number if challenged on "only compute what is needed": an ~8-node hot path inside a ~1030-node graph costs 984 ns per cycle on the dirty-list scheduler against 6.05 us for a naive full sweep — 6.2x apart. The naive dispatcher is kept as an executable oracle, same results either way.

Run modes

Backtest it, then run it live

runner.run(RunMode::HistoricalFrom(NanoTime::ZERO), RunFor::Forever)?;  // backtest

Two clocks, one of them yours

time() is source-driven — under replay it reads no clock at all. That is what makes a backtest deterministic.

A hang turned into an error

A live source rejects HistoricalFrom at wiring time, not at 3am.

This is the slide most of the audience actually wants, so do not rush it. ~75 seconds. The two-clock split is the whole determinism story: replay reads no clock, so the same input gives the same output every time; the wall snap is taken lazily on first read and cached in a Cell, so a cycle where nothing stamps reads the clock zero times — which matters because that read is ~24 ns. If asked "what about a graph that is partly live and partly replayed" — that is what the rejection above is protecting, and the honest answer is that you run two graphs.

The hook

127 levels deep. 2127 distinct paths. One tick.

That value is 2127 — the correct answer, which is also exactly the number of source→sink paths a framework that propagates one path at a time would have to walk.

THIS is the slide that wakes the room up. Land it slowly. "Every one of those 2^127 paths is a real path through the graph. A reactive library that pushes along one path at a time has to walk all of them. We visit 128 nodes." Pause. Then next slide explains why.

Why it stays flat

Visit each node once per tick

A node runs after everything it reads, exactly once — however many paths lead to it.

Propagate one path at a time and a shared node is re-visited per path. Branch and recombine, and that doubles every level.

Rx · async streams

Measured slopes 2.01× and 1.94× per level. Wingfoil: flat.

Be scrupulous here — a Rust audience will respect the honesty and punish the lack of it. Say out loud: the rxrust figure is HALVED from the raw ratio because its benchmark emits twice per sample; the tokio target is recursive Box::pin over an immediately-ready leaf, which is an honest depiction of per-path propagation but not the best an async implementation could do. The claim is the SLOPE, not the multiplier.

The engineering problem

What we wanted: compile the graph

Interpreted, every node pays a dynamic dispatch and a trip through a value slot — per node, per cycle.

On a hot chain that dominates the arithmetic you came to do.

So: generate code. One straight-line function, state in locals, optimiser working across node boundaries.

We built it

Ran the wiring from build.rs, walked the graph, emitted a runner.

It failed three ways — and the third told us why.

~75 seconds, and sell the plan honestly: it is a good plan, it is what anyone would try, and every ingredient really does exist. That is what makes the next slide land. The failure is not incompetence, it is a design constraint nobody had named yet.

Why a rewrite, not a feature

The generator failed three ways

1 It had to re-implement every node. Semantics were welded to RefCell fields, so generated code could not call a node's cycle. Two maps, two filters — nothing keeping them in step.
2 Types and closures were already gone. Wiring erased them. You cannot get |x| x * 10 back out of a Box<dyn Fn>.
3 Scheduling was inferred from names. Nothing declared "I schedule myself", so the engine drove nodes off allowlists.

Node semantics were not separately callable.

The argumentative core of the talk — take your time, roughly 30 seconds a wall. Wall 2 usually gets a laugh: a human re-typing the closure that already exists ten lines up, with no compiler check that the two agree. Then the punch, slowly. No amount of cleverness in the emitter fixes a design where there is nothing to emit a call TO. That sentence is why the engine got rewritten rather than extended.

The pattern

Inside-out

The tension

Encapsulation says bundle state with behaviour. Single responsibility says one reason to change. Follow the first far enough and you break the second.

The resolution

Encapsulate the logic and the types. Let ownership live outside.

Ownership moved out. Encapsulation didn't.
The op owns what and how. The engine owns where and when.

THE closing slide. ~90 seconds, and do not rush the last line. Three beats: the tension (everyone in the room has this problem), the resolution (ownership out, encapsulation in), then the payoff — the op owns what and how, the engine owns where and when — which is the promise made back on slide 3 being paid. Point at the arrow. That arrow IS the pattern: the engine passes state it cannot read into logic it cannot see. Neither side knows the other's interior, and that is why three different engines can drive one definition. Name the cousins OUT LOUD. A Rust room is already thinking "isn't this an ECS?", and getting there first turns a hostile question into agreement. The claim is the combination, not the shape.

Optional, if the room is warm and you want a name they will remember: the Japanese for an inside-out roll — rice outside, nori in — is "uramaki". Deploy it as a throwaway or skip it; nothing on the slide depends on it.

Q&A backup — the three things we would tell someone doing this rewrite, which used to be this slide: 1. Decide the contract questions first, in blast-radius order. Fallibility touched every op; deciding it late means retrofitting every emitter. 2. Point the dependency edge at the new thing — the old tree depended on the new one, so the last step was a deletion, not an archaeological dig. 3. Make the invariant structural, not aspirational. "Keep the paths in sync" is a promise that decays; "the second copy is a compile error" is a property.

The one decision everything follows from

Semantics became an associated function

trait Op {
    type Cfg;              // construction-time config; closures live here
    type State;            // engine-owned mutable state
    type In<'a>;           // typed inputs, passed in per cycle
    type Out;              // the produced value
    const ACTIVATION: Activation;

    fn cycle(cfg: &mut Self::Cfg, state: &mut Self::State,
             input: Self::In<'_>, ctx: &mut Ctx<'_>) -> Result<Tick<Self::Out>>;
}

Read what is absent. Nothing here says how state is stored, where inputs come from, or who calls it.

Not a method on an instantiated object — an associated function over explicit arguments. Every one of those four associated types is a hole the engine fills, and the engine gets to choose HOW it fills them. Don't rush to the payoff — make them look at the absence first. Plant the phrase here, in one sentence, without putting it on the slide: "this is an inside-out object — the logic stays wrapped, the state moves outside." Slide 20 is where that gets its name and its picture, so a room that has heard the phrase once already arrives at the close primed. If asked about the return type: Tick has THREE states, not two — Value ticks downstream, Quiet does neither, and Silent updates the value slot WITHOUT ticking, which is exactly what delay needs and the reason a "did it fire?" boolean is not enough. That was settled as a contract question up front rather than discovered while porting delay.

The same node, both ways

The node changed completely. The wiring barely moved.

legacy — the node owns everything

#[node(active = [upstream], output = value: f64)]
impl MutableNode for ScaleStream {
    fn cycle(&mut self, _state: &mut GraphState)
        -> Result<bool>
    {
        self.value =
            self.upstream.peek_value() * self.factor;
        Ok(true)
    }
}

owns: its upstream handles, its state, its output slot

let count = ticker(Duration::from_millis(10))
    .count();
count.run(RunMode::RealTime, RunFor::Cycles(100))?;

now — the engine owns everything

#[op(build = scale, fluent)]
impl Op for Scale {
    type Cfg    = f64;             // config
    type State  = ();              // engine-owned
    type In<'a> = (&'a f64,);      // passed in
    type Out    = f64;
    const ACTIVATION: Activation = Activation::NONE;

    fn cycle(cfg: &mut f64, _state: &mut (),
             input: (&f64,), _ctx: &mut Ctx<'_>)
        -> Result<Tick<f64>>
    {
        Ok(Tick::Value(input.0 * *cfg))
    }
}

owns: nothing — cfg, state and inputs all arrive as arguments

let g = GraphBuilder::new();
let count = g.ticker(Duration::from_millis(10))
    .count();
g.build().run(RunMode::RealTime, RunFor::Cycles(100))?;

The payoff slide for the whole rewrite argument, and the one that answers "did your users have to rewrite everything?" — no. Roughly 90 seconds. Top row: the node source is unrecognisable. `&mut self` with stored upstreams and RefCell fields becomes four associated types and a free function over explicit arguments. That is the inversion, in source. Bottom row: the wiring is one extra line. You hold a GraphBuilder and build sources on it instead of calling free functions. That is the entire user-facing cost of the change. If asked what else moved: Rc<dyn Stream<T>> became Stream<T>, a cheap Clone handle, and operator traits became extension traits. RunMode, RunFor and NanoTime kept their shape — both engines share one runtime core.

What it buys

Two engines, one copy of the semantics

EngineWho owns stateDispatch
Interpretedthe builder's slotsone dyn call per node
Compiledlocals in a generated fnmonomorphized, inlinable

One implementation — which is why they cannot drift.

…and you choose the boundary, not the engine

A nested island mounts the compiled emission as one node of an interpreted graph. Not a third engine — which is why it lands between the two.

Be precise here, because this is where an overclaim would get caught. Tier has two variants — Interpreted and Compiled — and WINGFOIL_TIER picks between them. The island is the compiled emission with an interpreted boundary, not a third thing. The seam is the part worth selling: you do not choose globally. On the three-node graph an island is a dead wash with the interpreter (1.40 ms vs 1.43 ms) because a boundary needs something to amortise against; on the bigger graphs it lands 2.2–10.2× ahead. That spread is what "it is the seam, not an engine" looks like in the numbers. If you ever find yourself writing a second copy of what a node does, that is the invariant breaking — the only one in the codebase treated as non-negotiable.

The front door

You write the wiring once, in plain Rust

wingfoil::nitro! {
    fn odds_evens(g: &GraphBuilder) -> Stream<String> {
        let count    = g.ticker(PERIOD).count();
        let is_even  = count.map(|i| i.is_multiple_of(2));
        let is_odd   = is_even.map(|b| !b);
        let odd_str  = count.filter(&is_odd).map(|i| format!("{i} is odd"));
        let even_str = count.filter(&is_even).map(|i| format!("{i} is even"));
        let labelled = odd_str.merge(&even_str);
        labelled
    }
}

Out comes odds_evens::interpreted(), odds_evens::compiled() and odds_evens::nested() — from the same tokens.

The wiring function stays valid, reviewable Rust either way. That property was deliberately never traded away: count is read three times, so it is a shared apex node — the macro derives a real DAG, not a chain.

The constraint worth stating: wiring must be straight-line. Values and per-element logic can be as procedural as you like — the TOPOLOGY cannot depend on runtime values, because compiled() monomorphizes one local per node and the node list has to be complete after parsing. If asked about loops: .map_n / .fan with a literal count.

…and this is what it becomes

Develop interpreted — it honours the tracing span features and supports dynamic graph surgery, neither of which the monomorphized tiers have. Deploy compiled. Tier::default() falls back to the build profile, so the usual workflow needs no call-site change at all.

That the tiers AGREE is not a hope — tests/macro_parity.rs runs this same diamond through both engines and pins the outputs equal. That test is the structural form of the invariant: the property stays true rather than merely intended.

Extensibility

Your op is not a second-class citizen

#[op(build = my_thing)]          // on your Op impl, in your crate
impl Op for MyThing { … }        // → the interpreted builder method

Within 2.4% of a built-in on the compiled path — no edit to the macro crate, no table to register in.

"That was the property we most doubted was achievable, and it is the one that most changes what the library is for." A library where third-party ops are second-class is a library you eventually fork. This one you extend.
