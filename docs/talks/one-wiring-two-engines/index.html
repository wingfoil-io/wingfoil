The problem

Everything ticks at a different rate

Market data arrives when the venue sends it — fast, irregular, and not on your schedule. Orders tick when you act. Fills tick when the venue decides. Nothing is aligned, and nothing shares a clock.

And you have to modulate the rates yourself

sample on another stream's tick · throttle to at most once per interval · window and buffer for a bounded look-back · distinct to drop repeats · merge and split to recombine.

Performance matters

The budget is nanoseconds per node, not microseconds. This is the workload where the framework's overhead — not your arithmetic — is what you are paying for.

90 seconds. Set up the whole talk here: three feeds, three rates, none of them aligned, and the rate itself is something you need to control rather than something handed to you. Be precise about the grouping, because someone will push back on the word "burst": the point is that many messages carry the SAME exchange timestamp — one aggressive order sweeping several levels is several fills at one instant. That is a property of the data, not of how fast you are reading it. Wingfoil delivers same-timestamp values together and never collapses them to latest-wins, because a strictly-monotonic clock means a split same-time group cannot be reassembled afterwards. Then: performance. Nanoseconds per node. That constraint is what rules out most of the obvious answers, which is the next slide.

The solution

You need a DAG

  • Wire a graph of calculations — declare it once, not a callback at a time.
  • Topologically sorted, so every node runs after everything it reads, exactly once per tick.
  • Only compute what is needed — per-cycle work tracks the nodes that are active, not the size of the graph.
  • You want the framework to abstract over what needs to be computed at what time — that is its job, not yours.

Rx fails

Propagates one path at a time, so a shared node is re-visited once per path.

Async streams fail

Same shape, plus a future per node per level and a poll to dispatch it.

Branch and recombine, and both of them double every level. Wingfoil stays flat.

This is the thesis of act one — state it flat, then spend the next two slides earning it. Don't over-explain "doubles every level" here; slide 6 is the demonstration and slide 7 is the chart. The fourth bullet is the one to lean on: the framework's job is deciding what to compute and when. Everything after this slide is how that is actually done. Backup number if challenged on "only compute what is needed": an ~8-node hot path inside a ~1030-node graph costs 984 ns per cycle on the dirty-list scheduler against 6.05 us for a naive full sweep — 6.2x apart. The naive dispatcher is kept as an executable oracle, same results either way.

That value is 2127 — the correct answer, which is also exactly the number of source→sink paths a framework that propagates one path at a time would have to walk.

THIS is the slide that wakes the room up. Land it slowly. "Every one of those 2^127 paths is a real path through the graph. A reactive library that pushes along one path at a time has to walk all of them. We visit 128 nodes." Pause. Then next slide explains why.

Why

Visit each node once per tick, in topological order

A node runs after everything it reads, exactly once, no matter how many upstream paths lead to it.

Libraries that propagate along one path at a time re-visit shared nodes once per path — so on branch-and-recombine their cost doubles every level while ours stays flat.

Measured slopes: 2.01× and 1.94× per level. Ours: flat.

Least squares over ten depths gives ≈ 68 ns + 22 ns × depth interpreted — one more node per level, while the path count runs to 1024.

Log scale. At depth 10: ~39× faster than rxrust, ~134× than tokio async streams. The flatness is the claim, not the multiplier — and both comparisons are written down with the caveats that cut against us.

Be scrupulous here — a Rust audience will respect the honesty and punish the lack of it. Say out loud: the rxrust figure is HALVED from the raw ratio because its benchmark emits twice per sample; the tokio target is recursive Box::pin over an immediately-ready leaf, which is an honest depiction of per-path propagation but not the best an async implementation could do. The claim is the SLOPE, not the multiplier.

Act two

We wanted to make it faster.

Transition, and a short one — say the line and move on. This is the pivot from "what it does" to "how it is built". You should be around the 8-minute mark here.

The one decision everything follows from

Semantics became an associated function

trait Op {
    type Cfg;              // construction-time config; closures live here
    type State;            // engine-owned mutable state
    type In<'a>;           // typed inputs, passed in per cycle
    type Out;              // the produced value
    const ACTIVATION: Activation;

    fn cycle(cfg: &mut Self::Cfg, state: &mut Self::State,
             input: Self::In<'_>, ctx: &mut Ctx<'_>) -> Result<Tick<Self::Out>>;
}

Read what is absent. Nothing here says how state is stored, where inputs come from, or who calls it.

Not a method on an instantiated object — an associated function over explicit arguments. Every one of those four associated types is a hole the engine fills, and the engine gets to choose HOW it fills them. Don't rush to the payoff — make them look at the absence first. Plant the phrase here, in one sentence, without putting it on the slide: "this is an inside-out object — the logic stays wrapped, the state moves outside." Slide 20 is where that gets its name and its picture, so a room that has heard the phrase once already arrives at the close primed. If asked about the return type: Tick has THREE states, not two — Value ticks downstream, Quiet does neither, and Silent updates the value slot WITHOUT ticking, which is exactly what delay needs and the reason a "did it fire?" boolean is not enough. That was settled as a contract question up front rather than discovered while porting delay.

The payoff

Three things invert at once

1 Semantics are separable from storage, so there is something callable to emit calls to. One copy, reachable from any machinery — rather than a code generator carrying its own copy of what each node does.
2 Types and closures are ordinary generic parameters, so they survive into generated code by construction. Nothing to reverse-engineer out of a name string, and no closure to make the user re-state by hand.
3 const ACTIVATION states scheduling behaviour where a machine can read it. NONE / SCHEDULES / THREADED / ALWAYS — a const, so the interpreter reads it at wiring time and the compiled emission folds it into a dispatch condition after monomorphization.
Fast — 60 seconds. Each of these three was a hard blocker for the code generator we tried to build first: it had to re-implement every node, it could not recover a closure out of a Box<dyn Fn>, and it drove scheduling off name-based allowlists. Mention that only if someone asks — the slide stands without it. The satisfying bit is that nobody designed three fixes: one change fixed three things, which is usually the sign it was at the right level.

What it buys

Two engines, one copy of the semantics

Not two implementations kept in sync by discipline and tests. One implementation — which is why they cannot drift.

…and you choose the boundary, not the engine

A nested island mounts the compiled emission as one node of an interpreted graph — monomorphized inside, one dyn call outside. Hot core compiled, edges left open for threaded sources and feedback. It is not a third engine, which is exactly why it lands between the two on every benchmark.

Be precise here, because this is where an overclaim would get caught. Tier has two variants — Interpreted and Compiled — and WINGFOIL_TIER picks between them. The island is the compiled emission with an interpreted boundary, not a third thing. The seam is the part worth selling: you do not choose globally. On the three-node graph an island is a dead wash with the interpreter (1.40 ms vs 1.43 ms) because a boundary needs something to amortise against; on the bigger graphs it lands 2.2–10.2× ahead. That spread is what "it is the seam, not an engine" looks like in the numbers. If you ever find yourself writing a second copy of what a node does, that is the invariant breaking — the only one in the codebase treated as non-negotiable.

The front door

You write the wiring once, in plain Rust

wingfoil::nitro! {
    fn odds_evens(g: &GraphBuilder) -> Stream<String> {
        let count    = g.ticker(PERIOD).count();
        let is_even  = count.map(|i| i.is_multiple_of(2));
        let is_odd   = is_even.map(|b| !b);
        let odd_str  = count.filter(&is_odd).map(|i| format!("{i} is odd"));
        let even_str = count.filter(&is_even).map(|i| format!("{i} is even"));
        let labelled = odd_str.merge(&even_str);
        labelled
    }
}

Out comes odds_evens::interpreted(), odds_evens::compiled() and odds_evens::nested() — from the same tokens.

The wiring function stays valid, reviewable Rust either way. That property was deliberately never traded away: count is read three times, so it is a shared apex node — the macro derives a real DAG, not a chain.

The constraint worth stating: wiring must be straight-line. Values and per-element logic can be as procedural as you like — the TOPOLOGY cannot depend on runtime values, because compiled() monomorphizes one local per node and the node list has to be complete after parsing. If asked about loops: .map_n / .fan with a literal count.

…and this is what it becomes

One function. One local per node. No dyn.

let mut __k = Kernel::new(run_mode, run_for);

let mut __cfg_wf_anon_1   = PERIOD;
let mut __state_wf_anon_1 = __wf_op_ticker_seed_state(&__cfg_wf_anon_1);
let mut __v_wf_anon_1     = __wf_op_ticker_seed_value(&__cfg_wf_anon_1);
// … one cfg / state / value local per node, 11 nodes …

let mut __dirty = [false; 11usize];
while __k.begin_cycle(&mut __dirty) {
    let __t_wf_anon_1 = /* activation */ && {
        let mut __ctx = Ctx::new(&mut __k, 0usize);
        match __wf_op_ticker_cycle(&mut __cfg_wf_anon_1,
                                   &mut __state_wf_anon_1, (), &mut __ctx)
              .context("node 0 (wf_anon_1: ticker) cycle")? {
            Tick::Value(__val)  => { __v_wf_anon_1 = __val; true  }
            Tick::Silent(__val) => { __v_wf_anon_1 = __val; false }
            Tick::Quiet         => false,
        }
    };
    // … 10 more, emitted in topological order …
}

The outcome we most doubted

Wiring is open. Stream is closed.

Combinators are extension traits, never inherent methods — so a downstream crate adds vocabulary that feels native without this crate knowing about it. Two public primitives: GraphBuilder::source and Stream::wire.

#[op(build = my_thing)]          // on your Op impl, in your crate
impl Op for MyThing { … }        // → the interpreted builder method
                                 // → the nitro! forwarders compiled emission dispatches through

A user-defined op gets interpreted and fully-compiled coverage, within 2.4% of a built-in — with no edit to the macro crate and no table to register in.

There is no per-op table in the macro. Built-in and user ops take the identical path. If you are editing a match arm to add an op, you are on the wrong road.

"That was the property we most doubted was achievable, and it is the one that most changes what the library is for." A library where third-party ops are second-class is a library you eventually fork. This one you extend.

The unglamorous half

I/O on your terms, not the framework's

Four ways a node can be driven — declared, not inferred

NONEfires when an upstream ticks
SCHEDULESalso wakes itself off the time queue — tickers, delays
THREADEDfed from another thread across the channel layer
ALWAYSbusy-spun every cycle — socket polling

It is a const, so the interpreter reads it at wiring time and the compiled tier folds it into a dispatch condition. Values sharing a timestamp ride one Burst and are delivered atomically — never coalesced to latest-wins.

Not locked into async

The graph core is synchronous and lock-free. Tokio lives at the edges — produce_async maps an async stream onto a typed graph edge — so I/O stays in the async world and compute stays in the graph. You are not made to pick one runtime for everything.

The unglamorous half

Three languages, one engine

Rust — the engine

The whole surface. Everything below is a view onto this, not a reimplementation.

Python — the same graph model, in a wheel

The same combinators and run modes. Write node bodies in Python, get results out as a pandas frame — and a plugin seam to author an op, a sub-graph or a whole adapter in Rust and call it from Python when a node gets hot.

TypeScript — the browser end of the web adapter

Decodes the wire format using the server's own codec compiled to wasm, so there is no second implementation of the format to drift.

What survives the boundary

A Burst stays atomic — values sharing a timestamp grouped, never latest-wins, never dropped, identically in both run modes. And per-hop latency stamps survive a hop from Python into a Rust node and back.

Keep it brisk — 45 seconds. The claim that matters is the last card: the semantics do not soften at a language boundary. A Python user gets bursts and latency tracing, not a simplified model. The plugin seam is the answer to "isn't Python going to be slow?" — you move the hot node to Rust without leaving the graph.

The unglamorous half

Backtest it, then run it live — same wiring

runner.run(RunMode::HistoricalFrom(NanoTime::ZERO), RunFor::Forever)?;  // backtest
runner.run(RunMode::RealTime,                      RunFor::Forever)?;  // live

Two clocks, and only one is yours

time() is engine time, source-driven. Under replay it is pure logic — the kernel pops the earliest scheduled callback and consults no clock at all. This is the only one business logic may touch, and it is what makes a replay deterministic.

wall_time() is this cycle's wall-clock snap, for latency stamping. A real clock read in both modes, so "time spent" means the same in a backtest as live. Never branch logic on it.

The failure mode we removed

A live source rejects HistoricalFrom at wiring time. A historical run block-collects its input up front, so an unbounded live tail would deadlock at start.

Rejecting it while you wire turns a hang into an error message — which is the difference between a bug you find in ten seconds and one you find at 3am.

This is the slide most of the audience actually wants, so do not rush it. ~75 seconds. The two-clock split is the whole determinism story: replay reads no clock, so the same input gives the same output every time; the wall snap is taken lazily on first read and cached in a Cell, so a cycle where nothing stamps reads the clock zero times — which matters because that read is ~24 ns. If asked "what about a graph that is partly live and partly replayed" — that is what the rejection above is protecting, and the honest answer is that you run two graphs.

The pattern

Inside-out

The logic is still behind a boundary. What moved is who owns the storage.

The tension

Encapsulation says bundle state with behaviour. Single responsibility says one reason to change. Follow the first far enough and you break the second — our old node was computation and storage and plumbing, and nothing outside could call one without the other two.

The resolution

Encapsulate the logic and the types. Let ownership live outside. Cfg and State are associated types — the engine holds them and cannot see inside.

Ownership moved out. Encapsulation didn't.
The op owns what and how. The engine owns where and when.

Cousins, and we claim no better: Redux reducers · ECS · Mealy machines. Ours is the combination — reducer-shaped semantics, opaque associated types, a const for scheduling.

THE closing slide. ~90 seconds, and do not rush the last line. Three beats: the tension (everyone in the room has this problem), the resolution (ownership out, encapsulation in), then the payoff — the op owns what and how, the engine owns where and when — which is the promise made back on slide 3 being paid. Point at the arrow. That arrow IS the pattern: the engine passes state it cannot read into logic it cannot see. Neither side knows the other's interior, and that is why three different engines can drive one definition. Name the cousins OUT LOUD. A Rust room is already thinking "isn't this an ECS?", and getting there first turns a hostile question into agreement. The claim is the combination, not the shape. Optional, if the room is warm and you want a name they will remember: the Japanese for an inside-out roll — rice outside, nori in — is "uramaki". Point the dependency edge at the new thing — the old tree depended on the new one, so the last step was a deletion, not an archaeological dig. 3. Make the invariant structural, not aspirational. "Keep the paths in sync" is a promise that decays; "the second copy is a compile error" is a property.
